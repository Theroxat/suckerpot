# M32 — Join the network in three commands

Status: proposal for review. Scope: `docs/ROADMAP.md`, section M32. Builds on M21 (anonymous
egress, collector), M28 (installer, signed images, updates), M29 (hub, `spn/1`, consensus, threat
model), M30 (feeds) and M31 (hub in production, abuse.ch submission).
Every address in this document is a placeholder from the documentation ranges (192.0.2.0/24,
198.51.100.0/24, 203.0.113.0/24, 2001:db8::/32) or `example.org`. The only real names are the
project's public hub and feed hosts, `relay.selfhostr.io` and `lists.selfhostr.io`. Key values are
placeholders (`<HUB_PUBLIC_KEY>`, `<FEED_PUBLIC_KEY>`); the orchestrator fills them in before the
release.

## 1. Goal

Today a person who only wants to help the network has to install the whole product: dashboard,
first-run wizard, a VPN account, then join in the UI. M32 adds a second way in.

1. **Participant mode.** Three commands and nothing else to set up except opening the printed
   ports:

   ```bash
   git clone --depth 1 --branch vX.Y.Z https://github.com/<owner>/suckerpot.git
   cd suckerpot
   ./scripts/install.sh --participant
   ```

   No dashboard, no admin account, no wizard, no API key, no VPN needed. Sensors, database,
   ingest and the network node only, in about 2 GiB of memory. Choosing this mode is the explicit
   consent to join. A random pseudonym is generated. `./scripts/status.sh` shows what runs and what
   was sent. Signed releases install themselves once a day unless turned off.
2. **Full mode** stays exactly as today (the owner's install does not change behaviour). A
   participant can switch to full mode later and keep its data.
3. **Verifier nodes.** A participant without a VPN never downloads malware. It only reports the
   download links attackers tried. When at least two independent nodes reported the same link, the
   hub asks a **verifier node** (role granted by the hub operator and turned on by the node; at
   first only the operator's own node) to fetch it through its collector and VPN, and to send back
   an attestation (sha256, size, file type, family). A malware-like attestation plus two reporters
   makes the link eligible for URLhaus.
4. **Hub address and key ship in the release**, with a key rollover that auto-updated
   participants follow without typing anything.

Hard requirements (from the owner, decided):
- Participant mode is opt-in by the act of choosing it. Full mode keeps the network off by default.
- A participant without a VPN may reach **only** the hub (and the feed host if feeds are on).
  Enrichment that needs the internet is off, the collector is off, nothing else leaves. Only one
  service has a route out.
- Full mode keeps "every outbound call through the VPN".
- Nothing sent out names the operator. Nodes stay pseudonymous. The hub keeps no client addresses.

## 2. Decisions

| # | Decision | Alternatives rejected, and why |
| --- | --- | --- |
| D1 | A participant without a VPN reaches the hub through **`hubproxy`**, a new tiny allow-list forward proxy (our own code, Python standard library only). It accepts only `CONNECT <allowed name>:443` and is the only service with a route out in that mode. Ingest keeps no route and no external DNS; its egress client points at `hubproxy` instead of `vpn` | (a) Give ingest a non-internal network: breaks "no route out" for the biggest attack surface on the host (it parses attacker data). (b) tinyproxy or squid with a filter: one more third-party image to pin, logs by default, filter syntax mistakes open the world. (c) An SNI-routing TCP proxy with a network alias for the hub name: needs DNS tricks inside ingest, and a stray client to another name would still hit the proxy. (d) Tor: about 100 MiB more, slow, and many front ends block Tor exits; kept as a later idea |
| D2 | The egress gate gets a **direct mode** with a host **scope**: in direct mode the gate is open only for requests whose host is in the scope (hub host, feed host). Every other worker sees a closed gate (`egress_direct`) and idles, with no new code path | A separate client factory for the network worker: two ways out of ingest, and the static egress test would need an exception |
| D3 | The **participant overlay** `docker-compose.participant.yml` turns the base file into the participant stack (api off through a profile that is never set, `vpn` loses its dependency on `api`, ingest joins the `hub-proxy` network). The base file only gains the `hubproxy` service under the new profile `direct` and two networks. With `COMPOSE_PROFILES=egress` and no participant overlay (the owner's install) the rendered stack is unchanged | Making `api` a profile in the base file: the owner's `.env` would need a new profile value, a behaviour change for every existing install |
| D4 | Membership in participant mode is requested by ingest itself at start, from a **consent record** the installer writes to `.env` (`NETWORK_CONSENT`), after showing the same consent list the dashboard shows | An API call during install: participant mode has no API. A flag alone without a record: no proof of what was agreed to, and no versioning of the consent text |
| D5 | **Hub defaults ship inside the signed images** (`netproto` package data) and are mirrored for host scripts. An explicit `.env` value always wins | A defaults file read only by compose: compose cannot fall back from an empty variable to a file, and a host file is not covered by the image signatures |
| D6 | **Hub key rollover** by release: nodes pin a set of up to three keys; the hub signs each answer with its primary key and, during a transition, also with an alternate key in a second header. Old nodes read only the first header | In-band key announcement signed by the old key: a stolen old key (the usual reason to rotate) could announce the thief's key. Nodes asking the hub for its key on `/v1/info`: trust on first use, no protection against a fake hub |
| D7 | **Auto-update runs on the host** from the user's crontab (systemd user timer as a fallback), calling `scripts/auto-update.sh`, which verifies a **signed release manifest** (cosign keyless, same identity as the images) before `git checkout`, then runs the existing `update.sh` with automatic rollback | An updater container with the Docker socket: root on the host from a container, and it needs an internet route, which breaks "one service with a route out". Watchtower-style tag following: no signature check, no backup, no rollback. A system-wide systemd timer: needs `sudo` (a prompt) at install; documented as an option |
| D8 | A **verifier attestation never counts as a sighting**. URLhaus eligibility (path B) is: ≥ 2 distinct eligible nodes reported the link, and a verifier attested malware-like content. A verifier's own sensor may be one of the two reporters | Counting the attestation as the second node: one participant plus the verifier could then list a link that only one sensor ever saw. Requiring the verifier to be independent from the reporters: the attestation is a reproducible fact (bytes and their hash), not an opinion, and the operator vouches for the verifier; at bootstrap the operator's node is also the busiest sensor, so excluding it would starve the queue |
| D9 | Verification uses **new endpoints** under `/v1` with protocol `spn/1`. No existing request or answer changes | Adding fields to `/v1/targets` or `/v1/info`: nodes parse answers strictly (`extra="forbid"`), so every pre-M32 node would fail. A new protocol `spn/2`: far too heavy for an additive feature |
| D10 | Clear links revealed for verification live in `verify_tasks`, not in `targets.value`; a candidate target stays blinded | Writing the value into the candidate target: it would reach `/v1/targets` the moment the target is confirmed, before the normal reveal rules, and widen what a hub seizure gives away |
| D11 | Participant mode is **not anonymous toward the hub** when no VPN is set: the hub's TCP stack (and a tunnel provider in front of it) sees the home address. Stated in the consent text, the docs and `status.sh`; a VPN remains one command away | Refusing to run without a VPN: the owner decided participants must not need one. Hiding the fact: dishonest |

## 3. Threat model delta

M29 §3, M30 §3 and the M21 invariants hold unless amended here.

### 3.1 New or changed assets

| Asset | Must not be harmed or learned |
| --- | --- |
| Participant's home address | Learned by anyone except the hub operator's TCP stack (no-VPN participants); never stored or logged by the hub |
| The verifier's VPN exit and fetch timing | Linked to the operator's identity or home address |
| The verifier as a tool | Turned into a fetcher of arbitrary URLs (SSRF, confused deputy, DoS amplifier, canary oracle) |
| Participants' hosts | Taken over through the update channel |
| URLhaus accuracy | A benign URL submitted because of Sybil reporters or a bad attestation |

### 3.2 New adversary moves

| # | Move | Mitigation | Residual |
| --- | --- | --- | --- |
| M1 | A3 (curious hub) or the hub's tunnel provider records the home address of a no-VPN participant and links it to the node key, the pseudonym and the observation sets | H1 unchanged: no client address stored or logged, rate limiting on an in-memory HMAC. Consent text and `status.sh` say it plainly. `./scripts/participant.sh vpn <file>` switches to the VPN path at any time | **Policy, not technique.** A hostile or compromised hub operator, or the tunnel provider, can link a no-VPN participant to its home address. The sensor address is the home address, already known to every attacker who hits it. This is the price of no VPN, accepted by the owner |
| M2 | A5 (network observer, the participant's ISP) sees connections to `relay.selfhostr.io` | TLS. Padding (4 KiB). One batch per day | Participation itself is visible to the ISP |
| M3 | Compromised ingest (a parser bug exploited by attack data) uses the new route | `hubproxy` allows `CONNECT` to the allow-listed names on 443 only; no plain HTTP, no IP literal, no other port; answers that resolve to non-global addresses are refused (no rebinding into the LAN). Sensors are not on any network with `hubproxy`. The host firewall rule (optional) drops everything from `sp-hubgate` but TCP 443 | A compromised ingest can send data to the hub only. Before M32, a no-VPN install had no way out at all; the hub is not attacker-controlled |
| M4 | Compromised `hubproxy` (it parses the `CONNECT` line from ingest) | Only ingest can reach it (internal `hub-proxy` network). Non-root, read-only, `cap_drop: ALL`, 48 MiB, 32 pids, no volume, no secret but the proxy password | An attacker who owns ingest and then `hubproxy` has a general route out of the host's address. Two exploits in a row, both in small code we own; fuzz tests on the parser |
| M5 | Sybil participants (two fake nodes, aged 14 days) steer the verifier to fetch a URL of their choice | Reporters must be **eligible** (age 14 days, 7 active days with data, reputation ≥ 0.3). The hub validates every revealed URL (`http`/`https`, public host, no IP in private, reserved or documentation ranges, no local or numeric names, never-list, M16 shared hosts, CDN/Tor exclusions, length ≤ 1024). Caps: `HUB_VERIFY_DAILY_CAP` (200) tasks a day for the whole network, `HUB_VERIFY_HOST_DAILY_CAP` (5) per host a day, one fetch per URL ever (two attempts at most). The verifier's collector applies all M21 guards again (SSRF validator on every hop, gluetun rebinding protection, size, time and quota caps, generic client identity, `GET` only, no cookies, no credentials) and **never follows links found inside a verification sample** (depth 0). **Review mode** (`HUB_VERIFY_MODE=review`, the default once enabled): the operator sees each URL before any verifier gets it | In `auto` mode two aged Sybils can make the verifier send up to 5 `GET` requests a day to any public host they choose. Effects: the host learns the verifier's VPN exit; a site with state-changing `GET` links could be poked (confused deputy); no amplification beyond the caps. Review mode removes this until the operator trusts the flow |
| M6 | A1 probe-response with a lower threshold: the attacker sends one unique URL to a set S of suspected sensors and watches its server; a verifier fetch proves ≥ 2 nodes in S | Tasks are released after a random delay (`HUB_VERIFY_DELAY_H`, uniform 6 to 30 h after the reveal). The reveal itself needs two **eligible** reporters, and each node submits a day late (N5). One URL yields one bit | Group testing with k = 2 instead of 5 and a feedback loop of days. As in M29, it can show that an address runs a sensor (already visible to anyone who connects to it), never which pseudonym. Stated in `docs/network.md` |
| M7 | Early reveal leaks more clear links to the hub (and to A4 on seizure): links seen by 2 nodes instead of k | Only links reported by ≥ 2 eligible nodes, only from nodes that opted in (`verify_reveals` in the consent), each reveal guarded on the node (self address, owner names). Clear links are deleted with the task (14 days after its end). A per-target canary is seen by one node and is never revealed | A seized hub holds clear links of the last 14 days that 2 or more nodes saw. These are attacker-chosen download links, not node data |
| M8 | A malicious participant fakes an attestation | Only nodes with the `verifier` role (operator grant) can lease tasks; results are accepted only for tasks leased to that node; one result per task and node | None |
| M9 | A compromised verifier lies (malware-like attestation for a benign URL) | Two eligible reporters are still required. Path-B submissions in `auto` need the two reporters to span two enrolment cohorts and the network to have `HUB_AUTO_MIN_COHORTS`; otherwise they wait for review. `hub.admin node role revoke` and `hub.admin abusech cancel` | Today the operator is the only verifier, so this equals "the operator lies" |
| M10 | Cloaking: the URL serves malware to the verifier and an innocent page to others, or the reverse | A submission states what the verifier fetched. Serving malware to anyone makes the URL a malware URL | Cloaked malware that hides from the verifier is missed (no false positive) |
| M11 | Release-channel attacker (stolen GitHub account, poisoned workflow) pushes a malicious release to every auto-updating participant | The manifest is signed keyless by the release workflow identity on a `refs/tags/v*` ref; the tag's commit must equal the signed commit; images must verify (M28); a release is installed automatically only after it is `auto_min_age_h` (48) hours old; never across a major version; off with one command | **A compromise of the project's GitHub identity is a compromise of every auto-updating participant.** The 48-hour window gives time to delete a bad release. The same holds for any auto-updating software; stated in `docs/updates.md` and at install |
| M12 | A fake hub, or a key-rollover trick | Pinned key set from the signed release (D6); explicit `.env` keys win; no in-band key learning | A malicious release can change the key (same as M11) |
| M13 | Self-address auto-confirmation is steered (an attacker plants `Host:` headers naming an address) | Learning already needs ≥ 3 distinct sources from ≥ 2 networks in a week and refuses addresses that attacked the node or that reports name. Auto-confirmation is on only in participant mode | Over-redaction only: the planted address is never shared by that node. It cannot make the guard pass a real self address |
| M14 | A participant has no GeoIP/ASN database (no internet), so research scanners are not tagged locally | The hub never-list holds scanner ranges (M29 §8.6); consensus and the M30 rules never list `scan`/`connect` | Scanner sources reach the hub as observations; they never become reportable |

### 3.3 Invariant changes

| # | Invariant (new or amended) | Enforced by |
| --- | --- | --- |
| I1′ | No container has a route to the internet except `vpn` (profile `egress`) **or** `hubproxy` (profile `direct`), never both, plus the inbound-only `sp-ingress` and `sp-dashboard`. | Compose + guardrails (§11.1) |
| I7 | `hubproxy` opens only TCP connections to names in `HUBPROXY_ALLOW` (at most 2, port 443, public DNS names, resolved to global unicast), and only after a `CONNECT` from an authenticated client. | `hubproxy` code + tests + guardrails |
| N1′ | Nothing is sent unless `NETWORK_ENABLED=true` **and** membership was requested by an admin in the UI (full mode) or by ingest from a valid `NETWORK_CONSENT` record (participant mode). | Worker + tests |
| N2′ | Every network call goes through `suckerpot_egress`: the VPN proxy (gate open), or `hubproxy` (gate open in direct mode, request host in scope). | Gate scope + static egress test |
| N16 | In direct mode every egress worker other than the network and feed workers sees a closed gate. The collector and analyzer never run. | Gate + compose profiles + tests |
| N17 | A node reveals a link early (before consensus) only if its consent lists `verify_reveals`, only for hashes the hub lists in `/v1/verify/reveals`, only values it holds, and only after the identity guard. | Worker + tests |
| N18 | A node fetches for the network only with `NETWORK_VERIFIER=true`, VPN egress (gate open in VPN mode), the collector enabled, and within `NETWORK_VERIFY_DAILY_CAP` / `NETWORK_VERIFY_HOST_DAILY_CAP`. Verification fetches never recurse (depth 0). | Worker + collector + tests |
| N19 | The node accepts a hub answer only if one of its signature headers verifies under one of the pinned keys (≤ 3). | `netproto` + tests |
| N20 | Auto-update installs only a release whose signed manifest names the tag's commit, whose images verify, that is old enough, and within the same major version; a failed health check rolls back. | `auto-update.sh` + tests |
| H8 | The hub hands verification tasks only to nodes with the `verifier` role, and creates them only from links that ≥ `HUB_VERIFY_MIN_REPORTERS` (2) eligible nodes reported and that pass the URL checks and caps. | `hub/verify.py` + tests |
| H9 | Clear links held for verification are deleted 14 days after the task ends. A task row holds no node id except the current lease, cleared when the lease ends. | Retention + tests |

| Service | Full (today) | Participant, no VPN | Participant with VPN |
| --- | --- | --- | --- |

| --- | --- | --- | --- |

| `HUBPROXY_ALLOW` | — | `relay.selfhostr.io:443` (plus `lists.selfhostr.io:443` with feeds on) | — |

### 4.2 `hubproxy` (new service, base file, profile `direct`)

```yaml
hubproxy:
  profiles: [direct]
  image: ${SUCKERPOT_IMAGE_PREFIX:-local/${COMPOSE_PROJECT_NAME:-unset}}-hubproxy:${SUCKERPOT_VERSION:-dev}
  build: {context: ., dockerfile: hubproxy/Dockerfile, args: {VERSION: ..., BUILD_KIND: source, COMMIT: ...}}
  <<: *hardening                       # read_only, cap_drop ALL, no-new-privileges, logging
  user: "10001:10001"
  environment:
    HUBPROXY_ALLOW: ${HUBPROXY_ALLOW:?HUBPROXY_ALLOW must be set in .env}
    HUBPROXY_PASSWORD: ${EGRESS_PROXY_PASSWORD:?}   # same secret ingest already holds
    HUBPROXY_MAX_CONNS: "8"
  tmpfs: ["/tmp:rw,noexec,nosuid,nodev,size=1m"]
  networks:
    hub-uplink: {gw_priority: 100}
    hub-proxy: {}
  mem_limit: 48m
  memswap_limit: 48m
  cpus: 0.25
  pids_limit: 32
  restart: unless-stopped
  healthcheck: {test: ["CMD", "python", "-m", "hubproxy.healthcheck"], interval: 15s, timeout: 3s, retries: 3}
  # no ports, no volumes, Docker's embedded DNS (needed to resolve the allowed names)
```

Behaviour (`hubproxy/hubproxy/`, standard library `asyncio` only, about 300 lines):

| Rule | Detail |
| --- | --- |
| Listeners | `:8888` proxy, `:8000` control (`GET /status` only), both on `hub-proxy` |
| Accepted request | `CONNECT host:443 HTTP/1.1` with `Proxy-Authorization: Basic egress:<password>` (constant-time compare). Request line ≤ 512 bytes, headers ≤ 4 KiB, 5 s to send them |
| Host check | Exact, lower-cased match against `HUBPROXY_ALLOW` entries. Not an IP literal. Port 443 only |
| Resolution | `getaddrinfo` in the proxy; every answer must be global unicast (not private, loopback, link-local, CGNAT, reserved, documentation, multicast); connect to the first good one, IPv4 only (the networks have no IPv6) |
| Answers | `200 Connection established`, or `403` (host/port), `407` (auth), `405` (any method but `CONNECT`), `502` (resolution or connect failed), `503` (over `HUBPROXY_MAX_CONNS`). Constant bodies |
| Tunnel | Byte relay, idle timeout 60 s, total 10 min, no TLS termination, no inspection |
| Logging | Counters only (`allowed`, `refused_host`, `refused_auth`, ...). Never an address, a host name from a refused request, or a header |
| Startup | Refuses to start if `HUBPROXY_ALLOW` is empty, has more than 2 entries, a non-443 port, an IP literal, a single-label or local-suffix name |
| Control | `GET /status` → `{"mode": "direct", "allow": ["relay.selfhostr.io:443"], "ok": true}` |

### 4.3 Networks (base file)

| Network | Docker name | `internal` | Members | Notes |
| --- | --- | --- | --- | --- |
| `hub-uplink` | `sp-hubgate` (fixed bridge name) | no | `hubproxy` only | `enable_icc: false`, masquerade on, no IPv6 |
| `hub-proxy` | `sp-hubproxy` (bridge name) | **yes** | `hubproxy`, `ingest` (participant overlay) | Like `egress-proxy` for `vpn` |

Host firewall (`scripts/host/firewall.nft`, optional, the owner's rule set unchanged otherwise):
from `iifname "sp-hubgate"`, accept `tcp dport 443 ct state new`, accept established/related,
drop the rest. `docs/install.md` tells participants how to apply it; without it, `hubproxy` itself
is the control.

### 4.4 Participant overlay `docker-compose.participant.yml`

```yaml
# Participant mode (M32). Structural changes only: no port, capability or volume change.
services:
  api:
    profiles: [dashboard]          # a profile no installer ever sets: api never starts
  vpn:
    depends_on: !reset {}          # vpn used to wait for api (vpn-config owner); see below
  ingest:
    networks: [backend, egress-proxy, hub-proxy]
  backup:
    mem_limit: 96m
    memswap_limit: 96m
```

- The `vpn-config` volume owner was fixed by `api` starting first. In participant mode `vpn` reads
  WireGuard settings from `.env` only (the M28 installer path), so the volume stays empty; the
  overlay keeps it mounted read-only and `scripts/ensure-volumes.sh` creates it with uid 10001.
- Ingest environment additions live in the base file (defaults keep full mode unchanged):
  `SUCKERPOT_STACK_MODE` (`full`), `EGRESS_MODE` (`vpn`), `NETWORK_CONSENT` (empty),
  `NETWORK_PSEUDONYM` (empty), `NETWORK_COUNTRY` (empty), `NETWORK_SHOW_COUNTRY` (`false`),
  `NETWORK_VERIFY_REVEALS` (`false`), `NETWORK_VERIFIER` (`false`),
  `NETWORK_VERIFY_DAILY_CAP` (`100`), `NETWORK_VERIFY_HOST_DAILY_CAP` (`3`),
  `SELF_TERMS_AUTO_CONFIRM` (`false`), `SELF_ADDRESS` (empty).
- Collector environment: `COLLECTOR_VERIFY_ENABLED` (`false`, set to `true` by ingest's verifier
  wiring only through `.env`).

### 4.5 Memory budget (participant, 6 recommended sensors, lowmem + participant overlays)

| Service | Limit | Typical use after a day |
| --- | --- | --- |
| `db` | 512 MiB | 150 to 250 MiB |
| `redis` | 192 MiB | 20 to 40 MiB |
| `ingest` | 320 MiB | 150 to 200 MiB (most workers off) |
| `backup` | 96 MiB | 10 MiB (idle shell) |
| `hubproxy` | 48 MiB | 15 to 20 MiB |
| 6 sensors × 128 MiB | 768 MiB | 40 to 60 MiB each |
| `migrate` | 256 MiB | one-shot, exits |
| **Steady total** | **1,936 MiB of limits** | **about 0.7 to 1.0 GiB** |

With a VPN: `vpn` 256 MiB replaces `hubproxy` (+208 MiB), `collector` 192 MiB and `analyzer`
256 MiB only when `COLLECTOR_ENABLED=true`. The installer turns low memory on below 6 GiB without
asking in participant mode, and sets `DB_MAX_SIZE_GB=4`. The 2 GiB floor of M28 stays. Swap is
recommended on 2 GiB hosts (`docs/install.md`).

## 5. Installer UX

### 5.1 Flags (additions to `scripts/install.sh`)

| Flag | Meaning |
| --- | --- |
| `--participant` | Participant mode. Implies `--images` (unless `--source`), `--sensors recommended`, `--lowmem auto` (no prompt), auto-update on, feeds off |
| `--full` | Full mode. On a fresh host, the same as today's default. On an existing participant install, switches to full (§5.5) |
| `--yes` | No prompt at all. With `--participant`, this **is** the consent (documented) |
| `--pseudonym NAME` | Use this pseudonym (M29 rules, checked locally first). Default: random |
| `--no-pseudonym` | No pseudonym: shown as `Node 3f9a1c07` |
| `--country CC` / `--show-country` | Optional, never detected; hidden by default (M29 k-rules apply) |
| `--wg-conf PATH` | Use a VPN (participant with VPN: profile `egress`, `EGRESS_MODE=vpn`) |
| `--verifier` | Ask to be a verifier: needs `--wg-conf`; turns on `COLLECTOR_ENABLED` and `NETWORK_VERIFIER`. The hub operator must still grant the role |
| `--no-auto-update` | Do not schedule automatic updates |
| `--feeds` | Also fetch the public feed (adds `lists.selfhostr.io:443` to `HUBPROXY_ALLOW`). Off by default: a participant has no dashboard to show it |
| `--self-address ADDR` | Optional own public address (writes `SELF_ADDRESS` and `INDICATORS_IGNORE`). Otherwise learned from traffic and auto-confirmed (§8.4) |
| `--repair` | Existing install: re-run volumes, start and schedule steps without changing settings |

Existing flags keep their meaning. In participant mode `--dashboard-*`, `--public-host`,
`--admin-*` and `--allow-lan` are refused (`these flags need --full`).

### 5.2 Steps in participant mode

Same ten-step frame as M28. Differences:

| Step | Participant behaviour |
| --- | --- |
| 1. Preflight | As today; adds `crontab` or `systemctl --user` detection (warning only) |
| 2. Settings | No question. With a terminal and no `--yes`: the consent screen (§5.3) and one `[y/N]` |
| 3. Ports | As today; with port 22 busy the SSH sensor maps to host port 2222 without asking (as `--yes` does today). Admin SSH port detected, never forwarded |
| 4. Secrets | As today (all `SECRET_VARS`, including `SETTINGS_ENCRYPTION_KEY` for the node key). `SESSION_SECRET` is generated but unused |
| 5. Admin hash | Skipped. Image verification of `ingest` replaces the api pre-pull |

## 6. Protocol changes (`spn/1`, additive)

### 6.1 Versioning

- Protocol string stays `spn/1`, prefix `/v1`. No existing endpoint, request or answer changes, so
  every pre-M32 node keeps working unchanged (they never call the new endpoints; old answers are
  byte-identical, checked by a golden test).
- New endpoints answer `404` (unsigned) on a pre-M32 hub. A node treats that as `hub_no_verify`
  and retries once a day.
- New error code `not_verifier` (403, signed). Old nodes never receive it.
- `GET /v1/info` is **not** changed (strict parsing on old nodes).

### 6.2 New endpoints

| Method | Path | Signed | Who | Body and answer |
| --- | --- | --- | --- | --- |
| GET | `/v1/verify/reveals` | yes | any member | → `{"items": [{"kind": "url", "value_b": "<64 hex>"}]}` (≤ 200). Only links **this node** reported in the last `HUB_VERIFY_URL_MAX_AGE_DAYS` (3) days that have an open task in `waiting_reveal` |
| GET | `/v1/verify/tasks?limit=<1..20>` | yes | `verifier` role | → `{"tasks": [{"id": "v_0123456789ab", "url": "http://198.51.100.9/x.sh", "lease_until": "2026-11-03T18:00:00Z"}]}`. Leases up to `limit` queued tasks for `HUB_VERIFY_LEASE_HOURS` (6). Not a verifier → `not_verifier` |
| POST | `/v1/verify/results` | yes | `verifier` role | `{"protocol": "spn/1", "items": [Result]}` (≤ 50) → `{"accepted": n, "rejected": n}` |

The early reveal uses the existing `POST /v1/reveals` with the same body. The hub accepts a reveal
when it matches a confirmed target (today) **or** a `waiting_reveal` task whose `url_b` the caller
reported; in the second case the clear value goes to `verify_tasks.url` only (D10).

`Result`:

```json
{"id": "v_0123456789ab", "outcome": "fetched",
 "sha256": "<64 hex>", "size": 48213, "file_type": "elf-arm", "family": "mirai"}
```

| Field | Rule |
| --- | --- |
| `id` | `^v_[0-9a-f]{12}$`, a task leased to the caller and not yet answered by it |
| `outcome` | `fetched`, `unreachable`, `http_error`, `too_large`, `timeout`, `refused` (the node's own guards said no), `skipped` (local cap) |
| `sha256`, `size`, `file_type`, `family` | Only with `fetched`: sha256 hex; `size` 1 to 67,108,864; `file_type` in `FILE_TYPES_V1`; `family` in `FAMILIES_V1` or null |

All bodies: padding, unknown fields refused, depth ≤ 6, 64 KiB cap, as every `spn/1` request.

### 6.3 Limits

| Limit | Default |
| --- | --- |
| Signed requests per node | 60/hour (unchanged). A participant adds 4/h (`/v1/verify/reveals` every 15 min); a verifier adds 8/h |
| Tasks per lease call | 20 |
| Results per call | 50 |
| Reveals per node per day | 2,000 (unchanged; early reveals count) |

### 6.4 Hub key set and dual signatures

- The hub signs every answer with its **primary** key in `X-SPN-Hub-Signature` (unchanged) and,
  when `HUB_SIGNING_KEY_ALT_FILE` is set, with the **alternate** key in `X-SPN-Hub-Signature-Alt`,
  over the same canonical answer string.
- A node pins a set of 1 to 3 keys (`NETWORK_HUB_KEY` accepts a comma-separated list). It accepts
  an answer when **either** header verifies under **any** pinned key. Pre-M32 nodes read only the
  first header and pin one key.
- `GET /v1/info` keeps `hub_key` = primary. A node checks it is in its pinned set (today: equal).

Rollover runbook (`hub/README.md`):

| Phase | Hub | Release | Who works |
| --- | --- | --- | --- |
| 0 | Primary K1 | Defaults `[K1]` | Everyone |
| 1 | `hub.admin gen-signing-key` makes K2; set as alternate. Answers carry K1 and K2 | Next release ships `[K1, K2]` | Everyone |
| 2 (≥ 30 days after the release; auto-updaters follow within about 3 days) | Swap: primary K2, alternate K1 | — | Nodes with `[K1, K2]`; pre-M32 nodes and nodes still pinning only K1 get `hub_signature` and stop (fail closed) |
| 3 (≥ 90 days) | Drop K1 | Release ships `[K2]` | Updated nodes |

- **Host move without a key change** (copy the key file): only DNS changes; no rollover needed.
  This is the recommended way to move the hub.
- **Emergency** (K1 stolen): swap at once and publish a release with `auto_min_age_h: 0` in its
  manifest (§9.2). Nodes on the stolen key fail closed until they update.
- An explicit `.env` key overrides the defaults (the owner's install, forks). `status.sh` and the
  dashboard warn when the pinned set does not contain the release default
  (`hub_key_differs_from_release`).
- The feed key works the same way: `NETWORK_FEED_KEY` accepts a list; M30 already signs with the
  next key during a transition (`.next.minisig`).

### 7.1 Migration `h0009_verify`


- No `inet` column, no client address (the M29 privacy test stays strict).
- The only node link in a task is the live lease (`lease_node`), cleared when the lease ends.
  Reporters are counted, never stored per task; the `url` candidate target's
  `target_contributors` (≤ 30 days, M29 H3) already holds who reported it, for reputation.
- Roles: `hub_api` gets SELECT on `node_roles`, SELECT/UPDATE on `verify_tasks` (reveal, lease),
  INSERT on `verify_attestations`; `hub_worker` gets the rest.

### 7.2 Worker job `hub/hub/verify.py` (hourly, after consensus)

1. **Off** unless `HUB_VERIFY_MODE` is `review` or `auto` (default `off`: no task, no early reveal).
2. **Create.** For each `url_b` observed in the last `HUB_VERIFY_URL_MAX_AGE_DAYS` (3) days by
   ≥ `HUB_VERIFY_MIN_REPORTERS` (2) distinct **eligible** nodes, with no task yet and no
   `abusech_submissions` row for its clear value: insert `waiting_reveal` with the counts.
3. **On reveal** (in the route, then validated here): `abusech.url_refusal`, never-list, M16
   shared hosts (suffix match), the M30 exclusions (allow-list, delisting, CDN, Tor; stale ranges
   → wait), length; then the per-host cap (`HUB_VERIFY_HOST_DAILY_CAP`, 5 per host per day) and the
   network cap (`HUB_VERIFY_DAILY_CAP`, 200 per day). Fail → `refused` with a code. Pass →
   `pending_review` (`review`) or `queued` with `release_at = now + uniform(6, 30) h` (`auto`).
4. **Leases.** An expired lease returns the task to `queued` (`attempts + 1`); after
   `HUB_VERIFY_MAX_ATTEMPTS` (2) → `failed`.
5. **Expiry.** `waiting_reveal`, `pending_review` and `queued` tasks whose `last_report_day` is
   older than 3 days → `expired` (stale links are rarely alive; one-shot links are mostly missed).
6. **Own fetches count.** A verifier node's own batch row for the same `url_b` with
   `fetched: true` and malware-like content (`malware.is_malware_like`) is recorded as its
   attestation; the task goes to `attested` without a lease.
7. `verify_daily` counters. Retention: tasks and attestations deleted 14 days after `ended_day`;
   `verify_daily` kept.

### 7.3 abuse.ch rule change (`hub/hub/abusech.py`)

URLhaus candidates come from two paths:

| Path | Basis | Rule |
| --- | --- | --- |
| A (today) | `consensus` | Confirmed `url` target with a revealed value fetched malware-like by ≥ 2 eligible nodes |
| B (new) | `verified` | A task in `attested` with at least one attestation `malware_like = true` from a node that **still** holds the `verifier` role, attested in the last 3 days; reporters (recomputed at queue time) ≥ 2 distinct eligible nodes; the clear URL passes every check of path A (`url_refusal`, never-list, exclusions) |

- Path-B rows are inserted with `basis = 'verified'`, `verify_task_id`, `target_id` = the `url`
  candidate target id (it exists: consensus keeps a candidate row for values seen by ≥ 2 eligible
  nodes), tags from the attestation's family and file type (`tags_for`).
- **Approval.** `HUB_ABUSECH_MODE=review`: every row waits for an operator (today). `auto`: path-B
  rows are auto-approved only if `HUB_VERIFY_MODE=auto`, the reporters span ≥ 2 enrolment cohorts,
  and the network has `HUB_AUTO_MIN_COHORTS` cohorts; otherwise they stay queued.
- **Liveness before sending** (`_one`): path A unchanged; path B needs the task still `attested`,
  not refused by the operator, the verifier still holding the role, and the URL not on any
  exclusion. The target state check (`confirmed`/`reported`) does not apply to path B (the target
  is a candidate).
- Withdrawals (`withdraw_target`, `withdraw_value`) cover both paths.
- **Feeds and reports do not change in M32.** One verifier fetch is not "fetched by 2 nodes"; using
  attestations for the outbound list is a later decision (§14).

### 8.6 Collector (verifier only)

- Rows with `origin='network_verify'` are fetched like any other, with every M21 guard and the
  shared daily quota, but **never** produce child fetch targets (links inside a verification
  sample are not followed) and never create local indicators.
- `COLLECTOR_VERIFY_ENABLED=false` makes the collector skip (`refused`) verification rows, so the
  collector's owner can stop the role without ingest.
- Samples keep the M21 quarantine rules. The Malware page shows "Fetched for network verification"
  on them (api field `origin`).

## 9. Automatic updates

### 9.1 Where it runs (D7)

| Option | Verdict |
| --- | --- |
| Updater container with `/var/run/docker.sock` | **Rejected.** The socket is root on the host. The container would need an internet route (registry, GitHub), so a second service with a route out, next to sensors that are attacked all day. One bug in it and the host is gone |
| Watchtower or similar | **Rejected.** Follows tags, no cosign check, no database dump, no rollback, no `git` update of the compose file |
| System systemd timer | Allowed as a documented option; not the default because it needs `sudo` (a prompt) |
| **User crontab** of the installing user (fallback: systemd user timer when lingering is on) | **Chosen.** No new privilege (the user already runs `docker`), no new network path inside the stack, the same code path as `just update`, visible with `crontab -l`. It is host code, a narrow exception to "nothing runs on the host except Docker", recorded in `CLAUDE.md` §3 by the docs task |

Schedule: one random minute between 03:00 and 05:59 local time, chosen at install
(`scripts/lib/schedule.sh`), plus a random sleep of 0 to 30 min, so a fleet does not update at
once. The cron line carries a marker comment (`# selfhostr-auto-update <project>`), so install
and removal are idempotent and never touch other lines.

### 9.2 Signed release manifest (`.github/workflows/release.yml`)

The release workflow adds `release-manifest.json` to each GitHub release:

```json
{"schema": "selfhostr-release/1", "version": "v0.6.0", "commit": "<40 hex>",
 "images": {"ingest": "sha256:<64 hex>", "hubproxy": "sha256:<64 hex>"},
 "network_defaults_sha256": "<64 hex>", "auto_min_age_h": 48, "major": 0}
```

signed with `cosign sign-blob --bundle release-manifest.json.sigstore.json` (keyless, same
identity rule as the images: `.github/workflows/release.yml@refs/tags/v*`). The workflow refuses
to run if `network_defaults.env` holds a placeholder.

`scripts/verify-release.sh vX.Y.Z` (pinned cosign container, as `verify-images.sh`): downloads
both files from the release, `cosign verify-blob --bundle` with the identity, then checks
`commit == git rev-parse vX.Y.Z^{commit}`, `version` equals the tag, and the defaults hash equals
the checkout's file. It prints the bundle's transparency-log time (the release age). `update.sh`
runs it in images mode before `git checkout`; for a release older than v0.6.0 (no manifest) a
manual update warns and goes on, an automatic one refuses.

### 9.3 `scripts/auto-update.sh` (called by cron)

1. `flock` on `.suckerpot-state/update.lock`; exit quietly when held.
2. Exit if `AUTO_UPDATE_ENABLED` is not `true`, if `.suckerpot-state/last-update.json` says an
   update never completed, or if the install mode is `source`.
3. `git fetch --tags`; target = newest `vX.Y.Z` tag with the same major, newer than the running
   version, not in `.suckerpot-state/bad-versions`.
4. `verify-release.sh target`; refuse if the release is younger than `auto_min_age_h`.
5. `update.sh --yes --auto target` (backup, checkout, `env-migrate`, verify and pull images, up).
6. Health (mode-aware, in `update.sh`): every started service healthy within 600 s;
   `SUCKERPOT_RUNNING_VERSION` of `ingest` (participant) or `api` (full) equals the target;
   `python -m ingest.network.cli status --json` answers.
7. On any failure after the code changed: `rollback.sh --yes` (restores the pre-update dump and
   the previous commit and images; events of the last minutes are lost), add the target to
   `bad-versions`, record the outcome. No retry of that version; the next release is tried.
8. Write `.suckerpot-state/auto-update.json`: `{last_run, last_result, from, to, error_code}`
   (constant codes). `status.sh` reads it.

Output goes to `.suckerpot-state/auto-update.log` (rotated at 1 MiB, no secrets). Turning off:
`./scripts/participant.sh auto-update off` (removes the cron line and sets the flag). Full mode can
opt in with `just set AUTO_UPDATE_ENABLED=true` plus `scripts/participant.sh auto-update on`;
it is off by default there, so the owner's install is unchanged.

## 14. Risks, open questions and later work

1. **No-VPN anonymity (M1).** Accepted by the owner; must stay visible in the consent screen,
   `status.sh` and `docs/participate.md`. A later option: Tor as a third egress mode.
2. **Release channel (M11).** One GitHub identity can update every participant. Later: two-person
   release approval (protected environment on the release workflow) and an independent
   transparency check of the manifest.
3. **k = 2 probe-response (M6).** Review mode and random delays slow it; it cannot be removed while
   two sensors are enough to queue a fetch.
4. **Stale links.** Most one-shot links die before a participant submits (N5 delays by design).
   Verification mainly catches long-lived droppers. Measure with `verify_daily` before tuning.
5. **Bootstrap.** A participant counts after 14 days; path B needs two eligible reporters. The
   owner's node is one of the first.
6. **Feeds.** Attestations do not feed the outbound list in M32. Candidate: count a verifier
   attestation as one of the two fetches for `payload_ip`, once review data shows it is safe.
7. **Hub move.** Copy the signing key with the move if possible (no rollover). Regenerating
   requires the §6.4 runbook and at least one release in between.
8. **Key values.** `<HUB_PUBLIC_KEY>` and `<FEED_PUBLIC_KEY>` are filled by the orchestrator at
   P12; the release workflow refuses placeholders.
9. **Host scheduler.** Some minimal hosts have neither `cron` nor lingering systemd user sessions;
   the installer then warns and `status.sh` shows "automatic updates not scheduled".
