# M36: Useful from the first node

Status: design, not implemented. Decisions that need the owner are marked **[OWNER]**.

## 1. Problem

The network confirms nothing until it has at least `HUB_MIN_NODES` (5) eligible nodes. With one or a few nodes it produces 0 targets, 0 reports and 0 feed entries, so a new member gets nothing back. M36 gives a member real value from day one without weakening anti-poisoning, Sybil resistance, anonymity, or the rule that one node's sighting changes nothing public.

## 2. What the code does today (findings)

| Fact | Where | Consequence for M36 |
| --- | --- | --- |
| External corroboration exists, but only **after** `count >= min_nodes`: it replaces the "twice the nodes" rule for `ip`, `payload_ip`, `c2_ip` seen by 5 to 9 nodes. It never lowers `min_nodes` | `hub/hub/consensus.py` `evaluate`, `hub/hub/external.py` | Candidate (b) is already implemented in its safe form. Nothing below k exists, by design |
| Single-node values never get a row; candidates need 2 eligible nodes and are never published | `consensus.load_groups` (`CANDIDATE_MIN_NODES = 2`) | Any "seen elsewhere" hint must be built on the same eligibility rules |
| The feed index validator rejects an unknown list id (`IndexList._consistent`, `LIST_IDS`) | `netproto/suckerpot_netproto/feeds/models.py` | A new list in `/v1/index.json` would make every older node reject the whole index. New lists need their **own manifest** |
| Every `spn/1` model is `extra="forbid", strict=True` on the node side | `netproto/suckerpot_netproto/models.py` `ProtoModel` | No new field may be added to an existing `spn/1` answer. M36 adds none |
| Nodes already look up indicators one by one at URLhaus and ThreatFox with their own abuse.ch key | `ingest/ingest/enrichment/intel.py` | Each lookup tells abuse.ch (through the VPN) what this sensor saw, and needs a key and a quota per node |
| A participant without a VPN reaches only the hub and the feed host (`hubproxy`, `MAX_ALLOW = 2`) | `hubproxy/hubproxy/config.py`, M32 D2 | Participants cannot reach abuse.ch at all today. Anything served from the feed host reaches them with no proxy change |
| The hub already fetches allow-listed public data through its proxy, fail-closed (size, shrink, redirect, format checks) | `hub/hub/feeds/external.py` (Tor and CDN ranges) | The same pattern can fetch bulk intel files |

## 3. Recommendation

Accept an adapted (a) plus a node-side integration, and an honest bootstrap screen. Reject lowered thresholds and sub-k hints.

1. **External tier (adapted a).** The hub downloads bulk exports from abuse.ch (URLhaus, ThreatFox, Feodo Tracker) on a fixed schedule through its proxy, filters them with the existing feed exclusions, signs them with the feed key and publishes them on the feed site under `/v1/external/`, with a separate manifest. The tier is a deterministic function of public sources: it is **never** intersected with network sightings, never enters `targets`, consensus, reports, abuse.ch submissions or the five network lists.
2. **Node integration (the member value).** A node fetches the external tier (whole files, so nobody learns what it looks for) and uses it locally:
   - the intel worker answers from the local copy first, which removes most per-indicator lookups (privacy and quota gain, and it works in participant mode and without an abuse.ch key);
   - `seen_here` marks external entries that already touched this sensor ("37 known malware hosts were named in attacks on your sensors this month");
   - the M16 local score treats a local hit exactly like today's URLhaus or ThreatFox answer (no new weight);
   - the Blocklists page shows an **External** card, clearly labelled "from abuse.ch, not confirmed by the SuckerPot network", and the verified local mirror can serve it to a firewall.
3. **Honest bootstrap state.** The Network page says, from fields that already exist (`/v1/info` thresholds, `/v1/network` totals, `/v1/node` `eligible_from_day`), that the network starts confirming at 5 eligible nodes, when this node becomes eligible, and what the member already gets meanwhile. No protocol change.
4. **Optional, off by default: free corroboration.** The hub may use its local copy of the same bulk data as one more source for consensus rule 5 and the feed high tier, in place of a per-value API call. It never counts as a node and never lowers k. **[OWNER]** (section 9, D4).

Why this is the right shape: with fewer than k nodes, any output derived from network sightings either reveals one member's sighting or lowers the Sybil cost. The only honest day-one value is (i) curated public intel delivered in a privacy-preserving way, and (ii) better use of the member's own data. Both are delivered without touching the consensus.

## 4. Options rejected or deferred

| Option | Verdict | Reason |
| --- | --- | --- |
| (a) as asked, external **intersected** with network sightings and published | Rejected | One node's sighting would change a public file. Oracle: an attacker submits a URL of their own to URLhaus (open to registered users), uses it in a drop on a suspected sensor, and watches the intersected list. This is exactly the probe M29 and M30 close with k-support |
| (b) lower `min_nodes` when an external source corroborates | Rejected | Does not help one node unless k drops to 1. AbuseIPDB scores can be raised by anyone filing reports, and URLhaus accepts public submissions, so corroboration is cheap for an attacker to manufacture. Today's rule (corroboration only replaces the 2k rule at k..2k-1) stays |
| (c) member-only "seen elsewhere in the network" counts below k | Rejected for M36 | With k-anonymity below the confirmation k, Sybils need only `k_hint - 1` aged nodes to learn whether a probed address hit a sensor: same oracle, cheaper. At k or above, the hint equals "candidate seen by k nodes", which is empty until there are k nodes. Revisit when the network has 10+ eligible nodes (section 10) |
| Hub as a lookup proxy (a node asks the hub "is X on URLhaus?") | Rejected | Real-time queries give the hub per-node timing finer than a day (breaks M29 day granularity), make the hub a quota sink and an amplifier for anyone with a node key |
| Each node fetches abuse.ch bulk files itself | Rejected as default | Needs a VPN route to abuse.ch (impossible for direct-mode participants), an abuse.ch account per member (an identity), N times the upstream load. Still possible for full installs via today's intel worker |
| Relaxed "bootstrap" thresholds on the public hub | Rejected | Acceptable on a test hub only, never on the public hub: the thresholds are the Sybil cost |
| Third-party lists with restrictive licences (Spamhaus DROP, commercial feeds) | Rejected | Licence forbids or restricts redistribution |
| STIX for the external tier | Deferred | MISP users can take the source feeds directly; keep v1 small |

## 5. Threat model delta

New asset: **X-snapshot**, the hub's filtered copy of the external sources (public data, no node data).

| Adversary | New move | Mitigation |
| --- | --- | --- |
| A1 attacker | Gets a victim's host listed at abuse.ch, so it lands in the external tier | Labelled external everywhere; never counted as a node, never in consensus count, network lists or reports; feed exclusions (never-list, CDN and cloud fronts, shared hosting, resolvers, Tor) applied; only curated record types (section 7.2); upstream removal propagates within one cycle; delisting page points to the source |
| A1 attacker | Uses the external tier as a sensor-discovery oracle | Impossible: the tier contains no node data, the same bytes are produced with zero members |
| A2 Sybil farm | Gains anything from the tier | Nothing: the tier does not depend on submissions |
| A4 hub compromise | Signs a forged external list | Same key and checks as M30 (signature, serial, expiry, sha256, file name in the trusted comment). Same blast radius as forging the network lists today |
| A7 fake hub / feed | Serves a stale external snapshot | `valid_until`, rollback refusal, stale entries never served by the local mirror (M30 N15 applies) |
| Amplifier abuse | Makes the hub fetch more or other URLs | Fixed source list in `hub/data/external.yaml`, fixed schedule; no node or public request can trigger an upstream fetch. Feed site stays static |
| abuse.ch itself | Learns which indicators members saw | Reduced: nodes answer from the downloaded copy first. The hub fetches whole exports, never per value |

Invariants (extend M30 N11 to N15):

| # | Invariant |
| --- | --- |
| X1 | The external tier is computed only from the X-snapshot and the hub exclusions. No table holding node data (`observations`, `targets`, `target_contributors`, `reveals`) is read by the external job. Enforced by a static test on the module imports and SQL |
| X2 | External entries never create, confirm, weight or extend a target, a report, an abuse.ch submission or an entry of the five network lists. Only D4 (off by default) may read the snapshot, as a boolean corroboration |
| X3 | The external manifest is separate (`/v1/external/index.json`). `/v1/index.json` and its five lists are byte-identical with the feature on or off |
| X4 | Hub fetches: https, default port, no redirect, no credentials in the URL, generic client identity, through `HTTPS_PROXY`, size cap, shrink check. Same code path as `hub/hub/feeds/external.py` |
| X5 | Node fetches go through `suckerpot_egress` to the host of `NETWORK_FEED_URL` only, as M30 N12. No new host, so no `hubproxy` change |
| X6 | Every UI string and file header that shows an external entry names the source and says it is not confirmed by the network |

## 6. Data flows

```
abuse.ch bulk exports ──(hub-worker, HTTPS_PROXY, hourly, fail-closed)──► X-snapshot (hub DB)
X-snapshot ──(exclusions, caps, breaker)──► /v1/external/*.{txt,v4.txt,v6.txt,nft,ipset,rsc,csv,json} + index.json + .minisig
                                                         │  (feed site, static, no logs)
node ingest ExternalFeedWorker ──(egress gate, VPN or hubproxy, GET only)──┘
   └─► network_external_entries ─┬─► intel worker: local hit = known, no API call
                                  ├─► seen_here (local SQL only)
                                  ├─► API /api/v1/network/external/* ─► Blocklists "External" card
                                  └─► verified local mirror /feeds/[token/]network/external-*.txt
[D4, off] X-snapshot ──boolean──► consensus rule 5 / feed high tier (never a node, never lowers k)
```

Nothing flows from a node to the hub in M36. No batch, request or answer of `spn/1` changes.

## 7. Feed format (additive, outside `spn/1`)

### 7.1 Files

Base `https://<feeds domain>/v1/external/`. Lists: `external-outbound` (payload hosts and C2 addresses) and `external-outbound-domains` (exact names). Formats as M30 for each list (`txt`, `txt-v4`, `txt-v6`, `nft`, `ipset`, `rsc`, `csv`, `json`; domains: `txt`, `csv`, `json`), plus `index.json`, `index.json.minisig`, `README.txt`. nft table `inet selfhostr_ext`, ipset names `external_outbound_v4/_v6`, so loading both tiers never collides with M30 sets.

`index.json`: schema `selfhostr-external/1`, same fields as `selfhostr-feeds/1`, plus `sources: [{id, name, licence, url}]` (attribution, constant per release). Its own `serial` sequence. Same feed key and trusted-comment rules.

Entry (`selfhostr-external-feed/1`):

```json
{"value": "203.0.113.45", "family": "4", "list": "external-outbound",
 "categories": ["payload-host"], "sources": ["urlhaus"], "families": ["mirai"], "ports": [],
 "first_seen": "2026-11-02", "last_seen": "2026-11-06", "expires": "2026-11-13"}
```

`categories` reuses the M30 closed set (`payload-host`, `c2`). `families` only when the source tag maps to `FAMILIES_V1`, else empty. `sources` in {`urlhaus`, `threatfox`, `feodotracker`}. `first_seen` and `last_seen` are the days the **hub** first and last saw the value in a source export (never a node day). No URL, no path, no reporter name, no source reference id, no free text.

### 7.2 Selection (per source)

| Source | Taken | Never taken |
| --- | --- | --- |
| URLhaus | `malware_download` URLs with status online, added in the last `HUB_EXTERNAL_MAX_AGE_DAYS` (30); the **host** only (IP literal to `external-outbound`, name to `-domains`) | Paths, URLs whose host is excluded (shared hosting, CDN, cloud storage names, which are a large part of URLhaus) |
| ThreatFox | `botnet_cc` IOCs of type `ip:port`, `domain`, with `confidence_level >= HUB_EXTERNAL_TF_MIN_CONFIDENCE` (75), last 30 days | `url`, hashes, other threat types |
| Feodo Tracker | The recommended C2 IP blocklist | Historical lists |

Then: M30 exclusions (`hub/hub/feeds/filter.py`, ranges must be fresh or the job stops with `ranges_stale`), canonical value checks, caps (20,000 per list), hold 0 h (the data is already public), change breaker with the M30 percentages, expiry 7 days after `last_seen`.

### 7.3 Compatibility

- Older nodes never request `/v1/external/`. `/v1/index.json` is untouched (X3).
- `netproto` gets new constants (`EXTERNAL_LIST_IDS`, directions, caps) and `ExternalIndexFile`. `LIST_IDS` and `IndexFile` do not change, so a new node keeps rejecting `external-*` inside the main index.
- No new `spn/1` endpoint or field. `protocols` in `/v1/info` stays `["spn/1"]`.

## 8. Configuration

Hub (`hub/.env.example`, passed by `hub/docker-compose.yml`, checked by `hub/tests/test_compose_env.py`):

| Variable | Default | Meaning |
| --- | --- | --- |
| `HUB_EXTERNAL_FEED_MODE` | `off` | `off`, `snapshot` (fetch and store only, for D4 or inspection), `publish` (also render and sign `/v1/external/`). Needs `HUB_FEED_MODE` not `off` for `publish` |
| `HUB_EXTERNAL_SOURCES` | `urlhaus,threatfox,feodotracker` | Subset of the sources in `hub/data/external.yaml` |
| `HUB_EXTERNAL_INTERVAL_MIN` | `60` | Fetch period per source (never below 30) |
| `HUB_EXTERNAL_MAX_AGE_DAYS` | `30` | Only recent records |
| `HUB_EXTERNAL_TF_MIN_CONFIDENCE` | `75` | ThreatFox threshold |
| `HUB_EXTERNAL_CORROBORATE` | `false` | D4: the snapshot answers rule 5 and the high-tier corroboration |
| (reused) `HUB_ABUSECH_AUTH_KEY` | empty | Sent as the `Auth-Key` header if the export endpoints require it **[OWNER]** D2 |

Node (`.env.example`, ingest and api):

| Variable | Default | Meaning |
| --- | --- | --- |
| `NETWORK_EXTERNAL_FEED` | `auto` | `auto` = on when `NETWORK_FEED_ENABLED=true` **[OWNER]** D3; `on`; `off`. URL is `NETWORK_FEED_URL` + `/external`, key is `NETWORK_FEED_KEY` (no new secret, no new host) |
| `NETWORK_EXTERNAL_LISTS` | `external-outbound,external-outbound-domains` | Lists stored |
| `INTEL_LOCAL_FIRST` | `true` | The intel worker checks `network_external_entries` before spending an API lookup. A miss still falls through to the API as today |

When the node feature is turned off, the worker wipes `network_external_*` on its next idle cycle (as `feed_disabled_wiped`). Leaving the network does not wipe it (public data, as M30).

## 11. Acceptance criteria

1. With `HUB_EXTERNAL_FEED_MODE=off`, the hub makes no request to abuse.ch export hosts and `/v1/external/` does not exist.
2. With `publish` and zero nodes enrolled, `/v1/external/index.json` verifies with the feed key and lists entries; `/v1/index.json` and the five lists are byte-identical to a run with the mode `off` (X3).
3. An external value never appears in `targets`, `target_contributors`, reports, `abusech_submissions` or the five network lists, whatever the network data (X1, X2).
4. An excluded value (shared hosting name, CDN range, resolver, Tor exit, never-list) is never in an external file.
5. A node built from the previous release fetches `/v1/index.json` and its lists without error while the external tier is live.
6. A new node with the feature on stores the external lists only after full verification (signature, serial, expiry, sha256), marks `seen_here`, and its intel worker makes no API call for an indicator found in the local copy.
7. A participant (direct mode, `--feeds`) receives the external tier with `HUBPROXY_ALLOW` unchanged.
8. Every screen and file header that shows an external entry names the source and says "not confirmed by the SuckerPot network".
9. The Network page of a member on a network below k shows the bootstrap sentence, the eligibility date and links to the external card; no new hub request is made for it.
10. `just guardrails`, `just egress-check`, `just check` and the hub test suite are green; `security-reviewer` passed.
