# M36: Useful from the first node

Status: design, not implemented. Decisions that need the owner are marked **[OWNER]**.

## 1. Problem

The network confirms nothing until it has at least `HUB_MIN_NODES` (5) eligible nodes. With one or a few nodes it produces 0 targets, 0 reports and 0 feed entries, so a new member gets nothing back. M36 gives a member real value from day one without weakening anti-poisoning, Sybil resistance, anonymity, or the rule that one node's sighting changes nothing public.

## 3. Recommendation

Accept an adapted (a) limited to CC0 sources, a node-side integration, and an honest bootstrap screen. Reject lowered thresholds and sub-k hints.

1. **External tier (adapted a), CC0 only.** The hub downloads the Feodo Tracker botnet C2 IP blocklist on a fixed schedule through its proxy, filters it with the existing feed exclusions, signs it with the feed key and publishes it on the feed site under `/v1/external/`, with a separate manifest. SSL Blacklist is added only if it still publishes an address list (**[OWNER]** D6). URLhaus and ThreatFox are **never** republished and never mirrored to nodes. The tier is a deterministic function of public CC0 data: never intersected with network sightings, never in `targets`, consensus, reports, abuse.ch submissions or the five network lists.
2. **Node integration.** A node fetches the whole external files (nobody learns what it looks for) and uses them locally:
   - the intel worker answers C2 address checks from the local Feodo copy first; URLhaus and ThreatFox lookups stay per indicator, as today, in full mode with a VPN and a key;
   - a participant or a node without an abuse.ch key gets known-C2 marks it has no other way to get;
   - `seen_here` marks external entries that already touched this sensor (for example an address a dropper tried to reach);
   - the M16 local score treats a Feodo hit like today's ThreatFox botnet C2 match (same level, reason text names Feodo Tracker);
   - the Blocklists page shows an **External** card, labelled "from abuse.ch Feodo Tracker (CC0), not confirmed by the SuckerPot network", and the verified local mirror can serve it to a firewall.
3. **Honest bootstrap state.** The Network page says, from fields that already exist (`/v1/info` thresholds, `/v1/network` totals, `/v1/node` `eligible_from_day`), that the network starts confirming at 5 eligible nodes, when this node becomes eligible, and what the member already gets meanwhile. No protocol change.
4. **Optional, off by default: internal corroboration (D4).** The hub may fetch URLhaus and ThreatFox bulk exports with its own abuse.ch Auth-Key, within the export limits, not for profit, and keep them internal as a boolean source for consensus rule 5 and the feed high tier, in place of per-value calls. Never published, never sent to nodes, never a node, never lowers k.

Expectation to set with members: Feodo Tracker is a small, high-precision list (tens to a few hundred addresses), so the external card is modest. Its worth is precision and privacy, not volume. The bootstrap screen says so.

Why this shape: with fewer than k nodes, any output derived from network sightings either reveals one member's sighting or lowers the Sybil cost. The only honest day-one value is curated public data delivered privately, plus better use of the member's own data.

## 4. Options rejected or deferred

| Option | Verdict | Reason |
| --- | --- | --- |
| Republish or mirror URLhaus and ThreatFox | Rejected | No licence statement; §7.3 forbids copying and derivative works without consent; not-for-profit access only |
| (a) external **intersected** with network sightings and published | Rejected | One node's sighting would change a public file. Oracle: an attacker gets an address of their own listed upstream, uses it on a suspected sensor and watches the intersected list. This is the probe M29 and M30 close with k-support |
| (b) lower `min_nodes` when an external source corroborates | Rejected | Does not help one node unless k drops to 1. AbuseIPDB scores and URLhaus listings can be manufactured. Today's rule (corroboration only replaces 2k at k..2k-1) stays |
| (c) member-only "seen elsewhere in the network" counts below k | Rejected for M36 | Sybils need only `k_hint - 1` aged nodes to learn whether a probed address hit a sensor: same oracle, cheaper. At k it equals "candidate seen by k nodes", empty until there are k nodes. Revisit at 10+ eligible nodes |
| Hub as a lookup proxy for nodes | Rejected | Per-node timing finer than a day (breaks M29 day granularity), quota sink, amplifier; also a redistribution of URLhaus and ThreatFox answers |
| Relaxed thresholds on the public hub | Rejected | Acceptable on a test hub only: the thresholds are the Sybil cost |
| Restrictive third-party lists (Spamhaus DROP, commercial feeds) | Rejected | Licence |
| STIX for the external tier | Deferred | Keep v1 small |

## 5. Threat model delta

New assets: **X-public**, the hub's filtered copy of CC0 sources, and (D4 only) **X-internal**, the latest URLhaus and ThreatFox exports. Neither holds node data.

| Adversary | New move | Mitigation |
| --- | --- | --- |
| A1 attacker | Gets a victim listed upstream so it lands in the external tier | Labelled external everywhere; never a node, never in consensus count, network lists or reports; feed exclusions applied; upstream removal propagates within one cycle; delisting page points to the source |
| A1 attacker | Uses the external tier as a sensor-discovery oracle | Impossible: no node data, same bytes with zero members |
| A2 Sybil farm | Gains anything from the tier | Nothing: the tier does not depend on submissions |
| A4 hub compromise | Signs a forged external list; reads X-internal | Same key and checks as M30. X-internal is upstream data the attacker could fetch anyway |
| A7 fake feed | Serves a stale snapshot | `valid_until`, rollback refusal, stale entries never served by the local mirror (M30 N15) |
| Amplifier abuse | Makes the hub fetch more or other URLs | Fixed source list in `hub/data/external.yaml`, fixed schedule; nothing a node or the public sends triggers an upstream fetch |
| Licence drift | A restricted source leaks into a public file | Each source in `external.yaml` declares `licence` and `publish`; the loader and a static test refuse `publish: true` unless `licence: CC0-1.0`, and refuse it outright for `urlhaus`, `threatfox`, `malwarebazaar` |

Invariants (extend M30 N11 to N15):

| # | Invariant |
| --- | --- |
| X1 | The external tier is computed only from X-public and the hub exclusions. The external job never reads `observations`, `targets`, `target_contributors` or `reveals` (static test) |
| X2 | External entries never create, confirm, weight or extend a target, report, abuse.ch submission or network list entry. Only D4 reads X-internal, as a boolean |
| X3 | `/v1/external/index.json` is a separate manifest; `/v1/index.json` and its five lists are byte-identical with the feature on or off |
| X4 | Hub fetches: https, default port, no redirect, generic client identity, through `HTTPS_PROXY`, size cap, shrink check (code path of `hub/hub/feeds/external.py`) |
| X5 | Node fetches go through `suckerpot_egress` to the host of `NETWORK_FEED_URL` only (M30 N12). No new host, no `hubproxy` change |
| X6 | Every UI string and file header showing an external entry names the source and says it is not confirmed by the network |
| X7 | X-internal never leaves the hub database: no file, no API answer, no report, no log line with a value. Only the latest export is kept; it is deleted when D4 is off. It is not used to train any model |

## 6. Data flows

```
Feodo Tracker (CC0) ──(hub-worker, HTTPS_PROXY, hourly, fail-closed)──► X-public
X-public ──(exclusions, caps, breaker)──► /v1/external/external-outbound.* + index.json + .minisig (feed site, static, no logs)
node ExternalFeedWorker ──(egress gate, VPN or hubproxy, GET only)──► network_external_entries
   ├─► intel worker: C2 address hit = known, no API call (URLhaus/ThreatFox lookups unchanged)
   ├─► seen_here (local SQL)    ├─► API /api/v1/network/external/* ─► Blocklists "External" card
   └─► verified local mirror /feeds/[token/]network/external-outbound.txt
[D4, off] URLhaus + ThreatFox exports ──(hub Auth-Key, export limits)──► X-internal ──boolean──► rule 5 / high tier
```

Nothing flows from a node to the hub in M36. No `spn/1` batch, request or answer changes.

## 7. Feed format (additive, outside `spn/1`)

### 7.1 Files

Base `https://<feeds domain>/v1/external/`. One list, `external-outbound` (C2 addresses), with the M30 address formats (`txt`, `txt-v4`, `txt-v6`, `nft`, `ipset`, `rsc`, `csv`, `json`), plus `index.json`, `index.json.minisig`, `README.txt`. nft table `inet selfhostr_ext`, ipset names `external_outbound_v4/_v6`, so loading both tiers never collides with M30 sets. No domain list (the CC0 sources hold addresses).

`index.json`: schema `selfhostr-external/1`, the fields of `selfhostr-feeds/1`, plus `sources: [{id, name, licence, url}]` (attribution is not required but given). Own `serial` sequence, same feed key and trusted-comment rules.

Entry (`selfhostr-external-feed/1`):

```json
{"value": "203.0.113.45", "family": "4", "list": "external-outbound", "categories": ["c2"],
 "sources": ["feodotracker"], "families": [], "ports": [443],
 "first_seen": "2026-11-02", "last_seen": "2026-11-06", "expires": "2026-11-13"}
```

`families` only when the source malware name maps to `FAMILIES_V1`. `first_seen` and `last_seen` are the days the **hub** first and last saw the value in the source (never a node day). No reference id, no free text.

### 7.2 Selection

Feodo Tracker recommended C2 IP blocklist (the source's own "recommended" subset), then: M30 exclusions (`hub/hub/feeds/filter.py`; stale ranges stop the job with `ranges_stale`), canonical value checks, cap 20,000, no hold (public data), M30 change breaker, expiry 7 days after `last_seen`. SSL Blacklist joins with the same rules only after D6.

### 7.3 Compatibility

- Older nodes never request `/v1/external/`; `/v1/index.json` is untouched (X3).
- `netproto` gets `EXTERNAL_LIST_IDS` and `ExternalIndexFile`. `LIST_IDS` and `IndexFile` do not change, so a new node still rejects `external-*` inside the main index.
- No new `spn/1` endpoint or field; `protocols` stays `["spn/1"]`.

## 11. Acceptance criteria

1. With `HUB_EXTERNAL_FEED_MODE=off` and D4 off, the hub makes no request to abuse.ch export hosts and `/v1/external/` does not exist.
2. With `publish` and zero nodes enrolled, `/v1/external/index.json` verifies with the feed key; `/v1/index.json` and the five lists are byte-identical to a run with the mode `off` (X3).
3. No URLhaus, ThreatFox or MalwareBazaar value appears in any file under the feed directory, any hub API answer or any node table, with D4 on or off (X7).
4. An external value never appears in `targets`, `target_contributors`, reports, `abusech_submissions` or the five network lists (X1, X2).
5. Excluded values (CDN range, resolver, Tor exit, never-list) are never in an external file.
6. A node from the previous release reads `/v1/index.json` and its lists without error while the external tier is live.
7. A new node stores the external list only after full verification, marks `seen_here`, and makes no API call for a C2 address found in the local copy; URLhaus and ThreatFox lookups behave as before.
8. A participant with `--feeds` receives the external tier with `HUBPROXY_ALLOW` unchanged.
9. Every screen and file header showing an external entry names Feodo Tracker and says "not confirmed by the SuckerPot network".
10. The Network page of a member below k shows the bootstrap sentence and the eligibility date, with no new hub request.
11. `just guardrails`, `just egress-check`, `just check` and the hub suite are green; `security-reviewer` passed.
