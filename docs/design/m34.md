# M34: public network observatory

## Goal

The project site (`suckerpot.selfhostr.io`, a static site maintained outside this repository) shows public, anonymised figures about the network: how many nodes there are, how close the network is to its first collective report, what consensus produced (confirmations, reports, takedowns) and what the network sees (attacks per day, most targeted services, most frequent tags and malware families).

The network starts with one node and no report, so every figure must stay honest and safe at that size: "1 of 5 nodes needed before the first collective report" is a valid page.

## Decisions

| Topic | Decision |
| --- | --- |
| File | `network.json`, schema `selfhostr-network-stats/1`, CC0 1.0 |
| Where | The feed site, next to `stats.json`: `https://<HUB_FEEDS_DOMAIN>/v1/network.json` (and its `.gz` sidecar). Same volume, same no-log, no-cookie, no-query policy |
| When | The worker rebuilds it once a day (first cycle after midnight UTC). Written with an atomic rename |
| Switch | `HUB_OBSERVATORY_ENABLED` (default `false`). Independent of `HUB_FEED_MODE`: the lists can stay off while the observatory publishes |
| Browser access | CORS for one origin, `HUB_OBSERVATORY_ORIGIN` (default `https://suckerpot.selfhostr.io`), and `Access-Control-Allow-Methods: GET`. Any method other than `GET` and `HEAD` gets 405, as for every feed file. A plain `GET` needs no preflight |
| Signature | None. The file is informational and is not listed in the signed feed index, which only exists when the feeds are on. Nothing consumes it automatically |
| Storage | One new table, `observatory_daily` (migration `h0010`): network-wide aggregates per final day, no node reference, kept 400 days. The worker role may insert, read and delete rows, never update them |
| Attacker countries and ASNs | Not published. The hub has no GeoIP or ASN database and the protocol sends neither; adding one is new data and out of scope |

## Data sources

Everything comes from tables the hub already has:

- **Nodes:** `nodes` (members, countries shown by choice), `batches` and the consensus eligibility rule (`consensus.eligible_nodes`: age, active days, reputation, standing).
- **Outcomes:** `targets.confirmed_day`, `reported_day`, `taken_down_day`; `reports` and `abusech_submissions` in state `sent`.
- **Activity:** `observations`, which are deleted after 14 days. A final day is therefore aggregated once into `observatory_daily`, from the observations of **eligible nodes only**:

| `metric` | `key` | `total` | `nodes` |
| --- | --- | --- | --- |
| `total` | empty | distinct attacking addresses (`kind = ip`) | eligible nodes that reported at least one attacking address (the k of the day) |
| `activity` | `login`, `command`, `download`, `exploit`, ... | distinct addresses with that activity | eligible nodes behind them |
| `service` | `ssh`, `telnet`, ... | distinct addresses on that service | same |
| `tag` | `mirai`, `recon`, `cve-...`, ... | distinct addresses with that tag | same |
| `family` | `mirai`, `xmrig`, ... | distinct files (`sha256`) of that family | same |
| `kind` | `payload_urls`, `files`, `c2` | distinct download links, files and C2 endpoints | same |

`nodes` is used by the rules below and never published.

Eligibility is taken at the time of the freeze, four days after the day, not on the day itself: batch markers are kept 14 days only, so the day's own 14-day look-back is no longer complete when the day becomes final. A node that is eligible on the day but not at the freeze is left out, which only makes the figures smaller and coarser.

## Anonymity rules (as implemented in `hub/hub/observatory.py`)

1. **Nothing per node.** No node id, fingerprint, pseudonym, key, address, reputation or tier, anywhere. A test walks the whole document and fails on any such key and on any value that looks like an address or a hex identifier.
2. **Only eligible nodes count.** Freshly enrolled or low-reputation nodes neither raise any threshold nor add to any figure. Two Sybils enrolled yesterday cannot unlock finer precision, and they cannot use the frozen union of sightings to test whether an honest node saw an address (tested: one honest node plus two fresh ones gives exactly the honest node's figures, coarse).
3. **Day granularity, with delay.** No time of day appears (`generated_day` is a date). Outcome figures stop two days back (`outcome_lag_days`), so the last published day ended at least 24 hours earlier. Activity figures stop four days back (`activity_lag_days`): a batch may arrive up to three days after its day, so only days that can no longer change are published.
4. **Frozen once.** A final day is aggregated once and never recomputed (and the database role cannot update it). A node that sends late, joins or leaves cannot move a number that was already published.
5. **Rounded counts.** Activity counts are rounded half up to two significant figures, never finer than tens (`1234` becomes `1200`, `3` becomes `0`). Shares are whole percentages.
6. **k = 3 eligible nodes, per figure.** A day is `standard` only when at least 3 eligible nodes reported attacking addresses that day; on a standard day each field also needs 3 eligible nodes behind it, otherwise it is `null`. Standard days are published day by day, but only for a complete ISO week in which every day is standard.
7. **Coarse otherwise.** Any other complete ISO week is ONE entry: the average per reporting day of `sources`, `login` and `command`, one significant figure; `download`, `exploit`, `payload_urls`, `files` and `c2` are `null`, because a few hundred attacker requests could move such small numbers. A week with no reporting node is all `null`. Partial weeks at the ends of the series are left out, so a published entry never changes shape later.
8. **No standard precision with relaxed eligibility.** If `HUB_NODE_MIN_AGE_DAYS`, `HUB_NODE_MIN_ACTIVE_DAYS` or `HUB_MIN_REPUTATION` is below its production default, every week and the 30-day lists are coarse.
9. **Named items need support.** Over the 30-day window:
   - standard: at least 20 address-days (or file-days) (`item_min`) and 2 eligible nodes on one day;
   - coarse: at least 100 (`item_min_coarse`), seen in at least 4 different ISO weeks (`item_min_weeks_coarse`), shares in steps of 5 points;
   - CVE tags carry digits chosen by the attacker and the hub has no list of known CVEs: a CVE tag always needs 2 eligible nodes on one day and is never named in coarse mode;
   - names are checked against the protocol allow-lists (`SERVICES`, `TAGS_V1` and CVE tags, `FAMILIES_V1`). At most 10 tags and 10 families.
10. **Outcomes depend on the consensus thresholds, enforced in code** (`outcome_precision`):
    - `exact` with production values (`HUB_MIN_NODES`, `HUB_MIN_WEIGHT`, `HUB_COHORT_MAX_SHARE` and the eligibility settings at their defaults or stricter): exact daily series and 30-day totals;
    - `rounded` when any of them is relaxed but `HUB_MIN_NODES` is at least 3: no daily series, totals per complete ISO week, and the `*_30d` totals taken over the last 4 complete ISO weeks instead of a sliding 30 days (a sliding sum would cross a rounding edge with day resolution), all rounded to tens, no median;
    - `suppressed` when `HUB_MIN_NODES` is below 3: no outcome number at all.
11. **Bootstrap once a week.** `nodes_missing` and `consensus_possible` are computed once per ISO week from batches before that week (eligibility as of the Monday) and kept until the next count. A week is counted only from its Thursday on, because the batch of the Sunday before can arrive until Wednesday; from Monday to Wednesday the previous week's count stays (a hub with no count yet counts the previous week). Batch markers are kept 14 days, so by Thursday the oldest three days of the look-back are gone: that can only lower the count. `active_last_week` counts the nodes that sent a batch in the previous ISO week. A node skipping a day changes nothing until the next week. No estimate of the first consensus day is published.
12. **Node countries need three members.** A country appears only when at least 3 members who chose to show a country share it (`MIN_COUNTRIES_SHOWN`).

### Why coarse rather than suppressed below three nodes

The owner wants attack figures from day one, as long as they cannot de-anonymise a node. These figures describe the attackers: how many addresses, on which services, with which tags. They contain no member address and no member location.

### Residual risks

- **Canary probing.** Someone who suspects that an address is a node can send traffic to it from many addresses and look for a jump. With one node, the coarse weekly average of `sources` (one significant figure) moves only when the probe is large compared to the background: with about 1,000 attacking addresses a day, a probe needs several hundred distinct addresses every day of a week, or a few thousand on one day, to change the published value reliably. When the background sits just under a rounding edge, a much smaller probe can tip it, but the prober cannot tell which edge case it is in. The low-volume fields, which about a hundred requests could move, are not published in coarse mode. The same probe already works against any reachable honeypot without this file ([network.md](../network.md#what-an-attacker-can-learn-about-your-sensors)), and it reveals that the address is a sensor, not who runs it.
- **Precision flips at exactly three nodes.** With exactly 3 eligible nodes, a week that turns `coarse` tells the reader that at least one of them sent no attacking address on at least one day of that week. It does not say which node or which day. The same holds for a field that is `null` on a standard day. The signal fades as the network grows.
- **Sensor set.** With one node, the service list shows which sensors that node runs. That says nothing about where it is or who runs it.
- **Bootstrap.** `nodes_missing` gives the exact number of eligible nodes below `min_nodes`, once a week. It moves when a node becomes eligible or stops being eligible for a whole week, not when it skips a day.

## Schema `selfhostr-network-stats/1`

Additive changes keep the schema id; a breaking change becomes `/2`. Every day is `YYYY-MM-DD` in UTC.

| Path | Type | Meaning |
| --- | --- | --- |
| `schema` | string | `selfhostr-network-stats/1` |
| `generated_day` | day | UTC day of the build |
| `licence` | string | `CC0-1.0` |
| `nodes.members` | int | Enrolled nodes |
| `nodes.active_last_week` | int | Nodes that sent a batch in the previous ISO week |
| `nodes.countries[]` | `{cc, members}` | Countries shown by at least 3 members |
| `bootstrap.week` | day | Monday of the ISO week the bootstrap figures were counted for (the previous week from Monday to Wednesday) |
| `bootstrap.min_nodes` | int | `HUB_MIN_NODES` |
| `bootstrap.nodes_missing` | int | Eligible nodes still needed, `max(0, min_nodes - eligible)` |
| `bootstrap.consensus_possible` | bool | `nodes_missing == 0` |
| `outcomes.first_day`, `last_day` | day | 90-day range, ending `outcome_lag_days` back |
| `outcomes.precision` | string | `exact`, `rounded` or `suppressed` (rule 10) |
| `outcomes.totals_first_day`, `totals_last_day` | day or null | Days the totals below cover: the last 30 days of the range (exact), the last 4 complete ISO weeks (rounded), null (suppressed) |
| `outcomes.confirmed_30d`, `reported_30d`, `taken_down_30d` | int or null | Targets that reached that state over the totals span |
| `outcomes.reports_sent_30d`, `abusech_sent_30d` | int or null | Abuse reports and abuse.ch submissions sent over the totals span |
| `outcomes.median_days_to_takedown` | int or null | Median days from report to takedown (exact mode only) |
| `outcomes.daily[]` | list or null | `{day, confirmed, reported, taken_down}` per day (exact mode only) |
| `outcomes.weekly[]` | list or null | `{start, confirmed, reported, taken_down}` per complete ISO week, rounded to tens (rounded mode only) |
| `activity.last_day` | day | Last final day (`activity_lag_days` back) |
| `activity.series[]` | object | Daily or weekly figures over up to 90 days (below) |
| `activity.window` | object | 30-day lists (below) |
| `rules` | object | The thresholds in force, so a page can explain them |

`activity.series[]` entries: `start` (day), `days` (1 for a standard day, 7 for a coarse week), `precision` (`standard` or `coarse`), then per-day figures, each an int or null: `sources` (attacking addresses), `login`, `command`, `download`, `exploit` (addresses with that activity), `payload_urls`, `files`, `c2`.

`activity.window`: `first_day`, `last_day`, `days` (30), `precision`, and three lists of `{id, share_pct}` sorted by volume: `services` and `tags` (share of attacking address-days), `families` (share of file-days).

## Operations

- Turn it on with `HUB_OBSERVATORY_ENABLED=true` in `hub/.env` and restart `hub-worker`. The file appears within one worker cycle. Turning it off stops the job; delete `network.json` from the feeds volume to unpublish.
- The file goes into `HUB_FEED_DIR` (the `feeds` volume, already mounted read-write in the worker and read-only in Caddy). Temporary files are named `.tmp-*`, which Caddy never serves.
- The weekly bootstrap counts are kept in `worker_state` (`observatory_week`).
- Retention: `observatory_daily` rows older than 400 days are deleted.
