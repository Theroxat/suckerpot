# M34: public network observatory

## Goal

The project site (`suckerpot.selfhostr.io`, a static site maintained outside this repository) shows public, anonymised figures about the network: how many nodes there are, how close the network is to its first collective report, what consensus produced (confirmations, reports, takedowns) and what the network sees (attacks per day, most targeted services, most frequent tags and malware families).

The network starts with one node and no report, so every figure must stay honest and safe at that size: "1 of 5 nodes needed before the first collective report" is a valid page.

## Decisions

| Topic | Decision |
| --- | --- |
| File | `network.json`, schema `selfhostr-network-stats/1`, CC0 1.0 |
| Where | The feed site, next to `stats.json`: `https://<HUB_FEEDS_DOMAIN>/v1/network.json` (and its `.gz` sidecar). Same volume, same no-log, no-cookie, no-query policy |
| When | The worker rebuilds it once a day (first cycle after midnight UTC), plus whenever a newly final day is frozen. Written with an atomic rename |
| Switch | `HUB_OBSERVATORY_ENABLED` (default `false`). Independent of `HUB_FEED_MODE`: the lists can stay off while the observatory publishes |
| Browser access | CORS for one origin, `HUB_OBSERVATORY_ORIGIN` (default `https://suckerpot.selfhostr.io`), and `Access-Control-Allow-Methods: GET`. Any method other than `GET` and `HEAD` gets 405, as for every feed file. A plain `GET` needs no preflight |
| Signature | None. The file is informational and is not listed in the signed feed index, which only exists when the feeds are on. Nothing consumes it automatically |
| Storage | One new table, `observatory_daily` (migration `h0010`): network-wide aggregates per final day, no node reference, kept 400 days |
| Attacker countries and ASNs | Not published. The hub has no GeoIP or ASN database and the protocol sends neither; adding one is new data and out of scope |

## Data sources

Everything comes from tables the hub already has:

- **Nodes:** `nodes` (members, countries shown by choice), `batches` (active and eligible nodes), the existing eligibility rule (`consensus.eligible_nodes`).
- **Outcomes:** `targets.confirmed_day`, `reported_day`, `taken_down_day`; `reports` and `abusech_submissions` in state `sent`.
- **Activity:** `observations`, which are deleted after 14 days. A final day is therefore aggregated once into `observatory_daily`:

| `metric` | `key` | `total` |
| --- | --- | --- |
| `total` | empty | distinct attacking addresses (`kind = ip`) |
| `activity` | `login`, `command`, `download`, `exploit`, ... | distinct addresses with that activity |
| `service` | `ssh`, `telnet`, ... | distinct addresses on that service |
| `tag` | `mirai`, `recon`, `cve-...`, ... | distinct addresses with that tag |
| `family` | `mirai`, `xmrig`, ... | distinct files (`sha256`) of that family |
| `kind` | `payload_urls`, `files`, `c2` | distinct download links, files and C2 endpoints |

Every row also has `nodes`, the number of distinct nodes behind it. It is used by the rules below and never published per day.

## Anonymity rules (as implemented in `hub/hub/observatory.py`)

1. **Nothing per node.** No node id, fingerprint, pseudonym, key, address, reputation or tier, anywhere. A test walks the whole document and fails on any such key and on any value that looks like an address or a hex identifier.
2. **Day granularity, with delay.** No time of day appears (`generated_day` is a date). Outcome figures stop two days back (`outcome_lag_days`), so the last published day ended at least 24 hours earlier. Activity figures stop four days back (`activity_lag_days`): a batch may arrive up to three days after its day, so only days that can no longer change are published.
3. **Frozen once.** A final day is aggregated once and never recomputed. A node that sends late, joins or leaves cannot move a number that was already published, so two versions of the file cannot be subtracted to isolate one node's contribution.
4. **Rounded counts.** Activity counts are rounded half up to two significant figures, never finer than tens (`1234` becomes `1200`, `3` becomes `0`). Shares are whole percentages.
5. **Coarse below three nodes.** A day with fewer than 3 contributing nodes (`min_nodes_standard`, the same k as `MIN_COUNTRIES_SHOWN`) is never published on its own. Its ISO week becomes ONE entry: the average per reporting day, one significant figure, or `null` when no node reported that week. Coarse entries always cover a complete ISO week; partial weeks at the ends of the series are left out until they are complete. The 30-day lists use shares in steps of 5 points while any reporting day in the window had fewer than 3 nodes.
6. **Items need support.** A service, tag or family is named only when it has at least 20 address-days (or file-days) in the window (`item_min`) and, once every reporting day of the window had 3 or more nodes, when at least 2 nodes saw it on one day. Names are checked against the protocol allow-lists (`SERVICES`, `TAGS_V1` and CVE tags, `FAMILIES_V1`) before they are published. Tags are capped at the top 10, families at the top 10.
7. **Node countries need three members.** A country appears only when at least 3 members who chose to show a country share it (`MIN_COUNTRIES_SHOWN`).
8. **Bootstrap figures are exact.** Members, active nodes and eligible nodes are counts of the whole network, already public in `stats.json`. `min_nodes` is read from `HUB_MIN_NODES`, never hard-coded.

### Why coarse rather than suppressed below three nodes

The owner wants attack figures from day one, as long as they cannot de-anonymise a node. What these figures describe is the attackers: how many addresses, on which services, with which tags. They contain no member address and no member location. The risks that remain with one node are:

- **Outage correlation.** A daily series would show the days a single node was off, which could be matched against a local power or ISP outage. Weekly averages over reporting days remove that signal.
- **Canary probing.** Someone who suspects that an address is a node can send traffic to it from many addresses and look for a jump. A 1-significant-figure weekly average absorbs a small probe; a large probe (hundreds of addresses on one day) could still move it. The same probe already works against any reachable honeypot, with or without this file ([network.md](../network.md#what-an-attacker-can-learn-about-your-sensors)), and it reveals that the address is a sensor, not who runs it.
- **Sensor set.** With one node, the service list shows which sensors that node runs. That says nothing about where it is or who runs it.

Suppression would hide the network's activity until three nodes exist, which defeats the purpose of the page. Coarse weekly figures give the shape of the traffic and keep the risks above small.

### Outcome counts are exact

Confirmations, reports and takedowns are exact daily counts. Each one already needed `HUB_MIN_NODES` independent nodes, and `stats.json` publishes the same kind of figure. A hub with relaxed development thresholds (`HUB_MIN_NODES` below 3) should keep the observatory off, because a confirmation could then rest on one node.

## Schema `selfhostr-network-stats/1`

Additive changes keep the schema id; a breaking change becomes `/2`. Every day is `YYYY-MM-DD` in UTC.

| Path | Type | Meaning |
| --- | --- | --- |
| `schema` | string | `selfhostr-network-stats/1` |
| `generated_day` | day | UTC day of the build |
| `licence` | string | `CC0-1.0` |
| `nodes.members` | int | Enrolled nodes |
| `nodes.active_7d` | int | Nodes that sent a batch in the last 7 days |
| `nodes.eligible` | int | Nodes whose sightings count for consensus today |
| `nodes.countries[]` | `{cc, members}` | Countries shown by at least 3 members (rule 7) |
| `bootstrap.min_nodes` | int | `HUB_MIN_NODES` |
| `bootstrap.eligible_nodes` | int | Same as `nodes.eligible` |
| `bootstrap.nodes_missing` | int | `max(0, min_nodes - eligible_nodes)` |
| `bootstrap.consensus_possible` | bool | `eligible_nodes >= min_nodes` |
| `bootstrap.first_consensus_day` | day or null | Earliest day the eligible count can reach `min_nodes` if the current nodes keep sending every day; null when there are not enough members yet |
| `bootstrap.days_until_first_consensus` | int or null | Days from `generated_day` to that day |
| `outcomes.first_day`, `last_day` | day | 90-day range, ending `outcome_lag_days` back |
| `outcomes.confirmed_30d`, `reported_30d`, `taken_down_30d` | int | Targets that reached that state in the last 30 days of the range |
| `outcomes.reports_sent_30d` | int | Abuse reports sent in those 30 days |
| `outcomes.abusech_sent_30d` | int | abuse.ch submissions sent in those 30 days |
| `outcomes.median_days_to_takedown` | int or null | Median days from report to takedown, same window |
| `outcomes.daily[]` | `{day, confirmed, reported, taken_down}` | One entry per day of the range |
| `activity.last_day` | day | Last final day (`activity_lag_days` back) |
| `activity.series[]` | object | Daily or weekly figures over up to 90 days (below) |
| `activity.window` | object | 30-day lists (below) |
| `rules` | object | The thresholds in force, so a page can explain them |

`activity.series[]` entries: `start` (day), `days` (1 for a standard day, 7 for a coarse week), `precision` (`standard` or `coarse`), then per-day figures, each an int or null: `sources` (attacking addresses), `login`, `command`, `download`, `exploit` (addresses with that activity), `payload_urls`, `files`, `c2`.

`activity.window`: `first_day`, `last_day`, `days` (30), `precision`, and three lists of `{id, share_pct}` sorted by volume: `services` and `tags` (share of attacking address-days), `families` (share of file-days).

## Bootstrap estimate

For each node in good standing that sent a batch in the last 14 days, the hub computes the first day it can be eligible if it sends every day from now on (age `HUB_NODE_MIN_AGE_DAYS`, `HUB_NODE_MIN_ACTIVE_DAYS` batch days out of 14, the same rule as consensus). The `min_nodes`-th earliest of those days is `first_consensus_day`. Only that one day is published, never a per-node date. It is the earliest day consensus is possible; a confirmation also needs several nodes to see the same attacker.

## Operations

- Turn it on with `HUB_OBSERVATORY_ENABLED=true` in `hub/.env` and restart `hub-worker`. The file appears within one worker cycle. Turning it off stops the job; delete `network.json` from the feeds volume to unpublish.
- The file goes into `HUB_FEED_DIR` (the `feeds` volume, already mounted read-write in the worker and read-only in Caddy). Temporary files are named `.tmp-*`, which Caddy never serves.
- Retention: `observatory_daily` rows older than 400 days are deleted.
